# Local web UI: Plan (v1, for design review)

Branch: `feature/ui`, cut from `origin/main`. Status: feature list agreed in outline. Screens are still to be
designed together.

**Goal:** a browser UI for the analyst laptop. It queues PCAPs, shows the merged CISA-14 inventory ranked fix-first,
lets the site team fill in the attributes passive capture can't, and manages the offline advisory index. All of this
runs on the existing jar.

> **Deviation from the proposal:** the proposal lists "A GUI. The HTML report is the interface." as out of scope. This
> plan adds a UI on top. The static `report.html` stays as the deliverable you can share, and the UI is an extra layer.

---

## 0. What exists today

```
ONLINE side (internet; GitHub Actions on deploy/github-actions, not yet on main)
  CISA CSAF OT feed + KEV ──build-index──► index.json + .sig (Ed25519) ──USB──┐
                                                                             ▼
OFFLINE analyst laptop (air-gapped)
  capture.pcap ─► analyze ─► observations.json ─► inventory ─► inventory.json/.csv/report.html
                     │                                (merge, CISA-14 score, match, fix-first rank)
                     └─ --post ─► serve (127.0.0.1:8088, in-memory) ─► /matches json|csv|html
```

| Piece | Where | What the UI can use |
|---|---|---|
| PCAP analyzer | `com.pcap.service.AnalysisService` | In-process call; it's in the same jar |
| Inventory/scoring/ranking | `com.advisory.Inventory`, `InventoryReport` | Today it only runs as the `inventory` CLI over files |
| Ingest API | `com.advisory.IngestServer` | 5 routes; runs only the old `Report` matcher; in-memory; no PCAP upload |
| Index | `AdvisoryIndex` | Metadata: `generated`, `kevCatalogVersion`, `advisories`, `rows`; signature verify |

Gaps: `serve` never runs `Inventory`, so scores, evidence and ranking aren't reachable over HTTP. Nothing persists
between runs. The parser has to push results with `--post`.

## 1. Decisions

| # | Question | Decision |
|---|---|---|
| 1 | One capture or many? | **Many, queued.** Captures run one at a time and merge into a single site inventory. |
| 2 | Who uses it? | **Site team** (§2). v1: one machine, loopback, every edit attributed to a named person, append-only change log. |
| 3 | `serve` on `Inventory` or `Report`? | **`Inventory`.** One pipeline for file mode and UI mode. `/matches` stays for `--post` compatibility. |
| 4 | Frontend stack | **Plain HTML/CSS/JS** in `src/main/resources/ui/`, served by the jar. No Node, no CDN, no build step. |
| 5 | `deploy/github-actions` | Merge it to main first (separate PR) so the UI can call `verify` and read `docs/deployment.md`. |

## 2. Site team: what the sources say

The proposal has no users or roles. It assumes one operator on one laptop. The CISA/NSA joint *Foundations for OT
Cybersecurity: Asset Inventory Guidance* (Aug 2025) is more specific. Relevant points and their effect on the UI:

| CISA guide says | UI consequence |
|---|---|
| "Assign roles and responsibilities for data collection **and validation**." (Step 1b) | Two jobs: **collector** (queues PCAPs, enters data) and **validator/owner** (confirms values). Fields show "unconfirmed" vs "validated by X". |
| "Identify asset inventory owners to oversee updates and validate asset classifications." | Each asset can have an owner. Validation is a recorded action. |
| "Establish a centralized database … implementing security controls to ensure data protection." (Step 4b) | The inventory is sensitive. It's stored on disk on the laptop, never synced out, and access is limited to the machine (v1). |
| "Use change management processes to accurately track OT asset modifications, additions, and decommissioning." | Append-only **change log**: who, when, field, old→new, source (capture id or human). |
| "Define the stages of each asset's life cycle (acquisition, deployment, commissioning, maintenance, decommissioning)." | A `lifecycle` field. A device that's gone stays listed as `decommissioned`, not deleted. |
| Classify by **criticality** or **function**; organize into **Zones and Conduits** (ISA/IEC 62443). | Criticality and role are editable. A `zone` field and a group-by-zone view. Conduits come later (§6). |
| "Validate and visualize … Cross-check collected inventory for accuracy and completeness." | The completeness score already exists. Add a "needs review" queue: conflicts, LOW confidence, unvalidated. |
| "Conduct regular reviews of the inventory." | Show the last review date, and differences between captures (new / changed / gone assets). |
| Cross-reference with KEV and CVE. | Already done by the matcher. |

**v1 scope:**
- Roles are labels on edits, not access control. The server stays on `127.0.0.1`, so whoever is at the laptop is
  trusted. That matches today's threat model.
- On first use the UI asks for a name and sends it as `X-Actor` with every write.

**v2 (not now):** LAN mode with real logins and roles. That means binding beyond loopback, TLS, sessions and CSRF
tokens, which is a separate security review.

## 3. Where it runs

- `java -jar reconnics-ng.jar serve --index … --pubkey … [--data DIR]`, then open `http://127.0.0.1:8088/`.
- One origin, so no CORS. Static files load from the classpath.
- **Host header check**: reject any request whose `Host` isn't `127.0.0.1:<port>` or `localhost:<port>`. This blocks
  DNS rebinding.
- Writes stay JSON-only (or `application/octet-stream` for PCAP plus a required custom header). A browser can't send
  either across origins without a preflight, and the server never answers preflights.
- The UI's own CSP: `default-src 'self'`, no inline scripts, no remote loads.
- State lives under `--data` (default `data/site/`): uploaded captures, observations, human edits, the change log and
  the active index.

## 4. Backend work

| # | Route / change | Notes |
|---|---|---|
| B1 | `GET /` and `/ui/*` | Serve static files from the jar's resources |
| B2 | `POST /api/v1/captures` | PCAP body streamed to disk (not the 16 MiB in-memory cap), SHA-256 computed while streaming. Returns `{id, state:"queued"}`. A duplicate hash is refused. |
| B3 | `GET /api/v1/captures`, `GET /captures/{id}`, `DELETE /captures/{id}` | Queue and history: `queued / running / done / failed`, analyze summary, errors (PCAPNG, unsupported link type). Delete only works on queued jobs. |
| B4 | Worker | One worker thread runs `AnalysisService`, then appends the observations. Captures merge in capture order; the firmware tie rule depends on that. |
| B5 | `GET /api/v1/inventory` | Runs `Inventory` over all observations plus human edits; returns `summary`, ranked `assets[]`, `rejected[]`. Cached until the next change. |
| B6 | `PATCH /api/v1/assets/{id}` | Human attributes (`criticality`, `location`, `asset_number`, `logging`, `user_accounts`, `zone`, `owner`, `lifecycle`) plus `validated`. Stored as observations with `confidence: HIGH, evidence: "entered by <actor>"`, so the existing merge handles them. |
| B7 | `GET /api/v1/changes` | Change log, newest first, filterable by asset |
| B8 | `GET /api/v1/index`, `POST /api/v1/index` | Status (age, verified/UNVERIFIED); import `index.json` + `.sig`, verify, then swap atomically |
| B9 | `GET /api/v1/export/{inventory.json,inventory.csv,report.html}` | The existing `InventoryReport` writers |
| B10 | Host check (§3) | Applies to every route |

## 5. UI features

**A. Overview**
- Asset count, average attributes filled out of 14 (passive max 9), fill rate per attribute.
- Match-ceiling distribution, and the count of KEV-listed advisories matched on vendor and model.
- Index banner: date, KEV version, verified/UNVERIFIED, stale after N days.
- Queue status, and the "needs review" count.

**B. Capture queue**
- Drop one or many PCAPs. Each shows its state, frames, malformed count, protocol candidates and identities decoded.
- Failures (PCAPNG, unsupported link type) shown with the fix to apply.
- History with hash, uploader and time, plus a diff against the previous capture: new / changed / gone assets.

**C. Inventory table (main screen)**
- Sorted fix-first.
- Filters: protocol, role, match level, KEV, conflict, zone, lifecycle, validated. Search by IP, MAC or name.
- Gateway units and backplane slots nested under their parent IP.

**D. Asset detail**
- The 14 attributes, each with value, confidence chip, evidence (frame number) and conflict/inherited marker.
- A "missing" list: who can fill each gap, with a hint, plus the next step for raising match quality.
- MAC and gateway notes, and `matchedAs` (S7 order number → product family).
- Matched advisories, and this asset's change history.

**E. Enrichment and validation**
- An edit form for the human attributes plus zone, owner and lifecycle.
- Bulk edit by role, subnet or zone, and a "mark validated" action.

**F. Review queue**
- Conflicts, LOW-confidence identity, unvalidated assets, and assets missing from the latest capture.

**G. Advisories**
- Per advisory: ID, title, CVEs, CVSS, KEV badge, affected assets.
- A NONE result reads "no matching advisory in index (generated <date>)", never "clean".

**H. Index**
- Import plus verify, a before/after summary, and a staleness setting.

**I. Exports and change log**
- Download JSON, CSV or HTML. Browse the change log.

**Not building:** live capture, scan or probe buttons, any upload or sync off the machine (`docs/ethics.md`).

## 6. Later

- Conduits view (zone-to-zone flows), which needs talker pairs from the parser.
- KEV `dueDate` / `knownRansomwareCampaignUse` in the advisory view. The index keeps only CVE, KEV ID and CVSS
  today, so this needs `IndexBuilder` changes.
- LAN multi-user mode with real auth (§2 v2).

## 6b. Graph view (added)

The start page is a BloodHound-style graph (see README tour): assets are nodes, observed conversations are directed, labelled edges,
advisories hang off assets. Every screen above is still there: the hamburger menu lists them, and they open as a sheet over the
graph (`#/inventory`, `#/captures`, ...) or, for one asset, as a side panel (`#/asset/ID`). Plain SVG with a small force layout
(no library, so the CSP stays `default-src 'self'`). The inventory table also lists the conversations, as the table twin of the graph.

Edges come from a new `flows` array that the analyzer writes (`ProtocolDetector` records them as it decodes; `FlowTable`) and
`GET /api/v1/inventory` returns, summed over captures. This covers the "talker pairs from the parser" item of section 6;
zone-to-zone conduits are still to do.

## 7. Open questions for the design session

1. Does a capture merge into the site inventory automatically, or does someone review it first and accept it?
2. Assets missing from the latest capture: flag them only, or offer to mark them `decommissioned`?
3. Zones: free text, or a list defined for the site?
4. How many days before the index counts as stale?
