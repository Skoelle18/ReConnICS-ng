## 3. Controlled loopback experiment

- Simulator: local lab workspace, `ReConnICS-lab/tools/modbus_loopback_demo.py`
- Bind address: 127.0.0.1
- TCP port: 15020
- Protocol: Modbus/TCP
- Request: function code 3, start address 0, quantity 2 registers.
- Expected response values: 123 and 456.
- Capture: local lab workspace, `ReConnICS-lab/captures/loopback-modbus.pcap`
- Capture size: 10 frames; tcpdump reported zero kernel drops.
- SHA-256: ffe52349c47f4bf4add1e142408dd4441a172a1013d87be583c3958453eaa57a
- Ground truth: `docs/examples/loopback-modbus-ground-truth.csv` in this repository
- ReConICS output: local lab workspace, `ReConnICS-lab/captures/loopback-inventory.json`

## 4. Observed results

- ReConICS processed all 10 frames.
- It reported 2 Modbus protocol candidates and 1 resolved asset.
- Detection basis: HEADER_VALIDATED.
- Output schema validation passed.
- Captured request payload: 000100000006010300000002
- Captured response payload: 000100000007010304007b01c8
- The response payload contains register values 0x007b (123) and
  0x01c8 (456), matching the simulator's expected values.
- ReConICS reported the loopback endpoint as 127.0.0.1 and the MAC as
  00:00:00:00:00:00. This MAC is a loopback artifact, not a physical
  device identifier.

## 5. Interpretation

The controlled test demonstrates basic Modbus/TCP recognition and
schema-valid inventory generation for this capture. It does not
demonstrate physical PLC identification, identity-field decoding,
detection accuracy across multiple assets, or performance on a full
GRFICS/OT network.

Wireshark labelled the request and response as unable to classify as
query or response. This should be investigated separately; it is not
evidence by itself that ReConICS parsed the messages incorrectly.

The existing sample and lab-generated loopback capture are different
datasets and must not be conflated.

## 6. Limitations and next tests

1. Investigate Modbus query/response classification on the controlled
   capture.
2. Test additional known Modbus function codes and malformed/truncated
   inputs using safe, deterministic fixtures.
3. Review why the existing sample produced no decoded device-identity
   fields despite containing Read Device Identification requests.
4. Establish a properly isolated representative OT lab before claiming
   GRFICS/OpenPLC/Conpot coverage.
5. Expand ground truth and measure false positives, false negatives,
   and identity-field accuracy before making accuracy claims.
